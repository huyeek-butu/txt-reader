# 基准设施 · PLAN-2026-1001-C（大文件性能与移动端）

> **「没有基准数据前不开始优化」** —— 这是 PLAN-C 的硬规矩。
> 本目录只做测量：不改动 `txt-reader.html` 一行代码。

## 快速开始

```bash
# 1) 生成样本（固定种子，逐字节可复现；样本约 42MB，已被 .gitignore 忽略）
node bench/gen-samples.js

# 2) 跑基准
node bench/run.js --label baseline                  # 全部样本 → bench/out/
node bench/run.js --rows 10000,100000               # 只跑指定档
node bench/run.js --label optimized                 # 优化后对比

# 3) 固化基线快照（结果入 bench/baseline/，会入库）
node bench/run.js --rows 10000,100000,500000 --label baseline --outdir bench/baseline
```

## 为什么不用 `--dump-dom` + `--virtual-time-budget`

虚拟时间模式下 `performance.now()` 走的是**虚拟时钟** —— 测出来的耗时不是真实耗时。
要拿真数字，必须连 CDP（Chrome DevTools Protocol），用 `Runtime.evaluate` 在页面内直接计时。
本设施用 Node 22 内置的全局 `WebSocket` 与 `fetch` 直连 CDP，**零依赖**，不引入 puppeteer / ws。

| `profile.js` | CPU 函数级采样（CDP Profiler），按 self time 聚合热点。**优化前必跑** —— 只知道「花了 1000ms」不够，得知道花在哪些函数上 |
| `mobile.js` | 移动端 / 触摸验证：CDP 设备模拟（375×812 / 812×375 / 768×1024）+ 真实 `Input.dispatchTouchEvent`。查触摸目标尺寸、横向溢出、纵向空间分配、侧栏抽屉、标尺触摸拖动 |
| `layout.js` | 窄屏 / 横屏**纵向空间下钻**：把 `.app` 纵向各段与顶栏 / 翻页栏子项的高度逐一提出来，定位「正文被谁挤没」。`mobile.js` 只给结论，这个脚本给证据 |
| `memory.js` | 内存泄漏验证：循环「打开 → 关闭」N 轮，每轮 `HeapProfiler.collectGarbage` 强制完整 GC 后再取 `JSHeapUsedSize`，看关闭点曲线是平的还是斜的 |

| `samples/` | 样本文件（忽略，不入库） |

## A/B 复测（判断「真回归」还是「环境漂移」的唯一办法）

同一次改动前后各测一轮，很容易把机器抖动当成回归。正确做法是把「改前」版本导出成文件，**交替轮流跑**：

```bash
git show <改前的提交>:txt-reader.html > bench/out/base.html
node bench/run.js --rows 100000 --file bench/out/base.html --label ab-base-r1 --port 9420
node bench/run.js --rows 100000 --file txt-reader.html      --label ab-opt-r1  --port 9425
```

跑 3 轮看中位数。**只有在同一次会话里交替跑出来的差异才能采信**（实测中「切不换行」首轮曾出现 +13% 的假回归，复测后反而是略快）。

## 测量口径

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **首屏可读时间** | 文件 `change` 事件 → `#content` 首次出现 `.row` | 页面内 `MutationObserver` |
| **读盘刻度** | 文件 `change` 事件 → `#stFile` 被写入（`state.bytes` 已就绪） | 同上 |
| **排版完成刻度** | → `#empty` 被隐藏（`applyLayoutToLines` 走完） | 同上 |
| **行数就绪时间** | 文件 `change` 事件 → `#stLines` 被写入（`computeLayout` 走完） | 同上 |
| **排版开关切换** | 同步点 `#layoutToggleBtn`，关 / 开各一次 | `performance.now()` 前后差值 |
| **字号变更** | 同步设 `#fontSelect` 24px → 28px → 还原 | 同上 |
| **换行模式切换** | 同步点 `#wrapSeg`，自动 → 不换行 → 自动 | 同上 |
| **滚动长任务** | 滚动 200 帧期间的 `longtask` 数量与最长时长 | `PerformanceObserver` |
| **内存** | `JSHeapUsedSize`、DOM 节点数、事件监听器数 | CDP `Performance.getMetrics` / `Memory.getDOMCounters` |

**三条诚实的保留**：

- **无头模式下不能采信帧率**。无头没有 vsync，`requestAnimationFrame` 间隔不代表真实刷新节奏。因此滚动流畅度用 `longtask` 作代理指标（长任务 = 主线程被阻塞 = 必然掉帧）。真实帧率需真机复测。
- **首屏包含 FileReader 异步读盘**，所以小样本上它会被 IO 抖动主导；比较时看的是**同环境下的相对变化**，不是绝对值。
- **`MutationObserver` 切不开同步块内部**。`openFile` 在 `state.bytes` 就绪之后是一整个同步块（解码 → 全文断句 → 全量视觉行 → 渲染），所有观察者回调都是微任务、在块末统一触发 —— 所以「读盘 / 解码+断句 / 排版+渲染」三列的分解**只在阶段间真的让出主线程时才有意义**，否则会看到后两列为 0。要拆同步块内部，得用 `profile.js` 的函数级采样。固定开销用极小样本（`--rows 200`）单独标定。

对照 PLAN-C 的目标口径（10 万行 · 桌面）：

| 指标 | 目标 | 基线 | 差距 |
|---|---|---|---|
| 首屏可读时间 | < 300 ms | 1009 ms | **3.4× 超标** |
| 排版开关切换 | < 150 ms | 603–871 ms | **4–5.8× 超标** |

**根因**（阶段一结论）：`computeLayout()` 每次都对**全部逻辑行**重跑 `wrapText` 并重建 `visualRows` / `offsets` / `pages`；更甚的是 `applyLayoutToLines()` 每次都重新解码全文、重跑全文断句，`Speak.setLines()` 还每次都重建整份朗读队列（哪怕根本没在朗读）。打开文件、改字号、松标尺、切排版，全走这一条路径且全程同步阻塞主线程。

## 窄屏纵向空间（阶段三新增指标）

`.app` 是**固定高度**的 flex 列（`height: 100vh`），正文 `min-height: 0` —— 于是顶栏/翻页栏一旦 wrap 失控，正文就被挤到 0。这个故障在只看宽度时不会暴露：812×375 横屏的**宽**是 812，窄屏媒体查询（`max-width: 768px`）根本不匹配，走的是桌面规则。

修前实测（`node bench/layout.js` 量取）：

| 视口 | 顶栏 | 翻页栏 | 正文视口 |
|---|---|---|---|
| 375×812 | 403 px | 166 px | **97 px** |
| 812×375 | 186 px | 155 px | **0 px**（完全不可读） |
| 768×1024 | 186 px | 101 px | 615 px |

处置与教训：

1. 约束挂在**高度**上（`max-height: 25vh` / `18vh` + 各自内部滚动），不挂在宽度媒体查询里 —— 否则横屏永远兜不住。
2. `flex: 0 0 auto` 不可省。给 `overflow: auto` 会把 flex 项的自动最小尺寸变成 0，于是顶栏反过来被正文**挤扁**：实测打开文件后顶栏被压到 26 px、翻页栏 18 px，比不设上限还糟。
3. `@media (pointer: coarse)` 的 `min-width: 44px` 必须配 `white-space: nowrap`。否则放不下的按钮被压到 44 px 宽，按钮内**文字按单字竖向折行**（「▶| 自动翻页 (空格)」实测被撑成 44×137），既撑高翻页栏又制造横向溢出。
4. 翻页栏的 `flex-wrap: wrap` 也得放在基础规则里：7 个控件自然宽合计约 747 px，812×375 横屏容器只有 490 px。

修后实测（`node bench/layout.js`，未打开文件；`mobile.js` 打开文件后正文会再少约 68px 给标尺与状态栏）：

| 视口 | 顶栏 | 翻页栏 | 正文视口 | 占比 | 横向溢出 |
|---|---|---|---|---|---|
| 375×812 | 203 px（13 控件，7 个需内部滚动） | 146 px（7 个，2 个需滚动） | **249 px** | 31% | 无 |
| 812×375 | 94 px（13 控件，8 个需滚动） | 62 px（7 个，3 个需滚动） | **53 px** | 14% | 无 |
| 768×1024 | 186 px（全部可见） | 101 px（全部可见） | **571 px** | 56% | 无 |
| 1440×900（对照） | 111 px（全部可见） | 54 px（全部可见） | 613 px | 68% | 无 |

桌面一栏是**边界确认**：上限规则虽写在基础规则里（不放进媒体查询，否则横屏兜不住），但桌面 1–2 行的高度远低于 25vh / 18vh，实测全部控件可见、正文 68%，规则不生效。

**这是一次有代价的取舍，不是白拿的**：手机竖屏下 13 个控件塞不进 343 px 宽，只能容下约 6 个；把顶栏限制在 203 px 意味着另外 7 个要在这个盒子内部下滑一点才能看到。换来的是正文从 97 px 回到 249 px —— 对阅读工具而言这个交换是划算的，但「手机上的紧凑顶栏」（例如把次要控件收进「⚙ 更多」浮层）仍是未做的工作。

横屏 53 px 仍不宽裕：375 px 视高要分给顶栏 / 翻页栏 / 标尺（44）/ 状态栏（约 40）四段。进入**纯净阅读模式**后顶栏、侧栏、翻页栏、状态栏全部隐藏，正文即占满全高 —— 那是横屏阅读的推荐路径。

## 内存泄漏验证的口径陷阱

`node bench/memory.js --rows 100000 --cycles 20`。

判定**不能**拿「空白页冷基线」当参照。冷基线是 0.6 MB，而跑过一轮 10 万行后，关闭文件的堆稳定在 12.7 MB —— 这 12 MB 是 V8 的**暖态**（引擎预热、已归还但未交还系统的缓冲），不是泄漏。首版就是拿冷基线做参照，于是把正常暖态误报成 `FAIL 存在累积（残留 12.2 MB）`。

正确参照是**首轮关闭后**的堆，看三件事：

| 判据 | 实测（10 万行 × 20 轮） |
|---|---|
| 关闭点曲线极差 ≤3 MB | **0.1 MB**（12.7 → 12.8） |
| 后半程均值 − 前半程均值 ≤3 MB | **0 MB** |
| 首末差 ≤3 MB | **0.1 MB** |
| 工作集确实释放 | 峰值 32.2 MB → 关闭 12.8 MB，释放 19.4 / 19.5 MB |
| 节点数 / 事件监听器 | 973 / 70，20 轮恒定 |

A/B 对照（同环境交替）：阶段二版本 12.7 → 12.8 MB，阶段三版本 12.7 → 12.8 MB —— **两者一致，均无泄漏**。（阶段三的 `invalidateDecode()` 增加了缓存载荷的显式释放，但 A/B 显示该释放原本就被后续调用顺带完成，**测不出差异**；保留它只是为了不依赖这种偶然性，不作性能声明。）

**下一步**（PLAN-C 要点 3 · 分片调度）仍待做：把「解码 + 全文断句」移出首屏关键路径，目标 10 万行首屏 < 300 ms（现 383 ms）。风险是视觉跳变与滚动锚点漂移，需要专项验证。

# 评估：TXT 阅读器加入 Markdown（`.md`）支持

> 类型：**可行性评估**（非冻结计划）。评估基线：`v1.16-btn-order`（提交 `6050028`，主文件 3 037 行 / 156 771 B）
> 日期：2026-10-03
> 结论一句话：**「读懂并干净地展示与朗读」低成本可行；「按 Markdown 语义真渲染」等于重写渲染内核。**

---

## 0. 先给结论

「支持 .md」这句话里藏着两种完全不同的需求，成本差一个数量级：

| 需求 | 实质 | 成本 | 可行性 |
|---|---|---|---|
| ① **读懂它** —— 别把 `#` `**` `>` 当正文念出来、别把 `-` 当标点 | 加一层「Markdown → 纯文本」预处理 | **约 150–250 行，1 个新模块** | **高**，与现有全部能力（排版/朗读/搜索/分页/进度/阅读模式）自动兼容 |
| ② **按语义渲染** —— 标题变大、列表出项目符号、代码块等宽、引用带竖条、表格对齐 | 需要**可变行高 + DOM 测量**的布局渲染内核 | **等于把 `computeLayout`/`buildPages`/`render`/`wrapText` 全部重做** | **低**，风险与工量与「重写一个阅读器」同阶 |

本仓当前内核是**定高虚拟滚动 + 逐字 canvas 测量 + 纯文本行**，这是 ② 的正面冲突点（详见 §2）。因此建议走 §5 的**方案 C：剥离 + 定高视觉增强**。

## 1. 现状盘点（决定了改造边界）

## 2. 为什么「真渲染」在当前内核上代价极高

四个耦合点，任一个破掉都会连锁：

1. **`offsets` 定高表** → 行高不等 ⇒ 滚动位置、`lowerBound()` 二分、`spacer` 高度全失效。要改成「行高数组 + 前缀和 + 增量重算」，复杂度上一个台阶。
2. **`buildPages` 按行数分页** → `rowsPerScreen = floor(vh / lineHeight)`。行高不固定后分页得改成按**像素累计**，且 `OVERLAP = 2 行` 的重叠语义也得换成像素。
3. **canvas 逐字测量** → 富块（列表缩进、代码缩进）需要 DOM 真实测量。混用两套测量会产生累积误差，`state.totalHeight` 与实际 DOM 高度不一致 → 滚动条抖动。
4. **虚拟窗口只渲染可视行** → 富块若跨行（表格、代码块）必须保证「不完整块不被切断渲染」，需要块级分组与占位高度预估（预估错就跳位）。

**结论**：不是加功能，是换内核。除非明确要把它做成 Markdown 阅读器，否则不划算。

## 3. 三种方案对比

| 维度 | **A · 纯文本剥离** | **B · 全量语义渲染** | **C · 剥离 + 定高视觉增强**（推荐） |
|---|---|---|---|
| 做法 | `md → 纯文本`，进现有管线 | `md → 块模型 → DOM 富渲染` | 剥离后**不改行高**，只给行打 `data-md` 类别 → CSS 上色/加粗/竖条 |
| 新增代码 | ~150–250 行 | 布局+渲染内核重写，2000 行量级 | ~300–450 行 |
| 动到内核 | 否 | 是（4 处耦合点全破） | **否**（`offsets` / `buildPages` / `wrapText` 全不动） |
| 排版 / 朗读 / 搜索 / 分页 / 进度 / 阅读模式 | 全部自动兼容 | 逐个适配 | 全部自动兼容 |
| XSS 面 | 无 | **有**（需净化器） | 无（不注入 HTML，只加 class） |
| 视觉收益 | 干净，但「不像 Markdown」 | 完整 | 约 80% 观感收益 |
| 风险 | 极低 | 高 | 低 |
| 定位 | 立即可用的最小闭环 | 另一个产品 | **甜点位** |

## 5. 解析与渲染的具体设计

### 5.1 解析层：单遍行扫描状态机（不用正则堆叠）

已有 `Layout` 的教训是「连续标点规则用正则堆叠会互相咬」，Markdown 语法嵌套更多，因此改为**逐行状态机**：

```
状态：normal | fenced-code | indented-code
对每行：
  fenced-code 中 → 直到闭合围栏，整行原样保留
  normal 中 → 依次判定块级前缀：
    ^#{1,6}\s         → h1..h6
    ^``` | ^~~~        → 进入 fenced-code
    ^>\s?             → quote（可累积层级）
    ^(\s*)([-*+]|\d+\.)\s → li（含 [ ] / [x] 任务列表）
    ^(-{3,}|\*{3,}|_{3,})\s*$ → hr
    ^\s*\|.*\|\s*$     → table（连续行归块）
    ^\s{4,}\S          → indented-code
    空行              → 段落边界
    其他              → 段落续行
行内（在 run-in 阶段处理）：**粗** / *斜* / ~~删~~ / `代码` / [文](链) / ![alt](src) / <自动链接> / \转义
```

**输出中间表示**（可测）：

```js
[ { type: 'h2',         level: 2, text: '标题',    inline: [...] },
  { type: 'p',          text: '正文…',             inline: [...] },
  { type: 'li',         ordered: false, depth: 1, marker: '-', text: '项目', inline: [...] },
  { type: 'quote',      depth: 1, text: '引用',     inline: [...] },
  { type: 'code',       lang: 'js', lines: ['…'] },
  { type: 'table',      align: [...], rows: [[...]] },
  { type: 'hr' } ]
```

### 5.2 文本路（进现有管线）—— **关键设计点**

必须在**块边界处产出 `\n\n`**，否则 `Layout.simpleLayout` 会按句重排，把标题和正文黏成一段、项目符号被吃掉。对应规则：

| 块类型 | 剥离后输出 | 理由 |
|---|---|---|
| 标题 | `标题文本` + 前后各一空行 | 独立成段，避免与正文合并 |
| 段落 | 原文本 | 交给 `simpleLayout` 按句分段 |
| 列表项 | `• 项目文本`（有序 `1. `）保留前缀字符 | 保留可见的项目符号，否则一列项目变成一坨 |
| 引用 | 文本 + 前后空行 | 与正文分开 |
| 代码块 | **原样保留内容**（含缩进，不参与断句） | 代码断句会被改坏；需在 `simpleLayout` 前用「保护段」标记跳过 |
| 表格 | 逐行 `a | b | c`（去分隔行 `---`） | 定高下无法对齐，只保证可读 |
| 图片 | `[图片：alt]` 占位 | 无法渲染（见 §6） |
| 链接 | 只留显示文本（可选附 URL 到行尾） | `.tx` 无 `<a>`，不可点 |
| 分隔线 | 一行 `────────` | 视觉可辨 |
| 行内标记 | 去 `**` `*` `~~` `` ` ``，保留文字 | 这是「念出来不别扭」的核心 |

### 5.3 视觉路（定高增强）—— 只加 class，不破约束

```
rowMeta[i] = 'h1' | 'h2' | ... | 'li' | 'quote' | 'code' | 'hr' | ''
render():  '<div class="row" data-md="' + (vr.md || '') + '" …>'
CSS:      仅改 .tx 的 font-weight / color / 内阴影 / ::before 装饰
```

**为什么不注入真 HTML**：① 会引入 XSS 面（markdown 允内联 HTML，需净化器）② 会破坏 `escapeHtml` + `<mark>` 的高亮偏移约定（§1 #8）③ 一旦插入块级元素就突破了定高（§2）。加 class 三条全避。

### 5.4 不做真 HTML 注入的安全依据

`render()` 的 `txHtml` 只有两条来源：`escapeHtml(vr.text)` 与 `highlightVisualRow()`（内部同样逐段 `escapeHtml` 再插 `<mark>`）。方案 C **不改变这条链路**，因此**不新增任何 XSS 面** —— 这是它相对方案 B 的一个被低估的优势。

## 6. 限制与取舍（诚实清单）

| 限制 | 原因 | 处置建议 |
|---|---|---|
| **图片无法显示** | **分两种情况**（已复核，勿想当然）：<br>① 用「打开文件」选 .md（`fileInput` @563）→ **无目录上下文**，相对路径无从解析，这是最常见的打开方式；<br>② 用「打开文件夹」载入（`folderInput` @567，`webkitdirectory`）→ 相对路径字符串**确实保留**在 `path`（@2266），但因 @2262 筛子只放行 `.txt`/`text/plain` 而**根本没进内存**。<br>且没有 FSA 目录句柄可用（打开侧无 FSA，@988 只有保存）。 | 方案 C 一律占位 `[图片：alt]`。<br>真要显示需同时满足三件事：① 放宽加载筛子、缓存非文本资源 ② 建 `blob:` URL 并按 md 所在 `path` 做相对路径解析 ③ 在 `.tx` 里插 `<img>` —— 第 ③ 件**同时突破定高并重新引入 XSS 面**。因此属于 P2 且需先有 `PLAN-C` 的布局改造 |
| **表格无法对齐渲染** | 定高 + 逐字折行，画不出列宽对齐 | 逐行降级为 `a | b | c`，可读即可 |
| **代码块无等宽字体** | 换字体需 `applyFont` 支持多字体 + 清 `widthCache`，否则折行宽度算错 | P1 再做；P0 仅保留缩进与换行 |
| **代码块不可参与断句** | `simpleLayout` 会按句号切代码 | 需加「保护段」机制（`Layout` 需小改，暴露跳过标记） |
| **链接不可点击** | `.tx` 只吃转义文本 | 只显示文本；要可点需放开 `<a>` → 又回到 XSS 面 |
| **标题字号不变** | 变字号 = 变行高 = 破定高 | 用**字重 + 颜色 + 装饰**代替字号，观感收益已足够 |
| **任务列表 checkbox 不可交互** | 需 `<input>` | 用 `☐` / `☑` 字符表示 |
| **数学公式 / 脚注 / 折叠 / 定义列表不支持** | 超出 P0 范围 | 原样保留文本 |
| **导出语义需二选一** | 「与屏幕一致」会丢掉原始语法，「导出原文」与所见不同 | 需你拍板（见 §7 选项） |

## 7. 工作量与建议分期

| 期 | 内容 | 规模 | 交付形态 |
|---|---|---|---|

## 8. 待你拍板

1. **深度**：A 纯剥离 / **C 剥离+定高增强**（推荐）/ B 全量渲染 / 暂不做
2. **导出语义**：导出「与屏幕一致（剥离后）」还是「原始 Markdown」（或两者都给）
3. **入口范围**：只放行 `.md`，还是一并放行 `.markdown` / `.mdx`（后者语法超集，会导致部分内容异常）
4. **次序**：先做 Markdown（P0/P1）还是先做 `PLAN-C`

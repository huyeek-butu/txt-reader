## 1. 目标

让 10 万行以上 TXT 与平板/手机上的滚动、排版切换、标尺拖动依旧流畅。

## 2. 解决的问题

| 问题 | 现状证据 |
|---|---|
| 全量重算导致卡顿 | `computeLayout` 对视觉行仅"采样估算"，但排版开关切换、标尺松开、字号变更均为**全量重算** |
| 移动端未适配 | 标尺 / 快捷键 / 侧栏均为桌面布局，仅 `.empty` 与标尺有零星 media query |
| 缺乏性能基线 | 未做过真实大文件基准，"卡不卡"属**未测**而非"没问题" |

## 3. 实现要点

1. **先量化再优化**：造 1 万 / 10 万 / 50 万行样本，测首屏时间、滚动帧率、排版切换耗时、内存峰值。**没有基准数据前不开始优化**。
2. **增量重排**：`Layout.simpleLayout` 改为**按可视窗口分段计算 + 缓存**，只重算进入视野的逻辑行；已算部分复用。
3. **分片调度**：`requestIdleCallback` 分块填充排版结果，避免长任务阻塞主线程（保留 `setTimeout` 降级）。
4. **响应式**：
   - ≤768px 侧栏改抽屉式
   - 标尺改触摸拖动（`pointerdown/move/up` 统一鼠标与触摸）
   - 触摸目标不小于 44×44px
5. **内存**：超大文件下避免同时持有 原文数组 / 视觉行数组 / 排版副本 三份全量数据，考虑弱引用或分段释放。

## 4. 性能目标（验收口径）

| 指标 | 目标值 | 测量条件 |
|---|---|---|
| 首屏可读时间 | < 300ms | 10 万行，桌面 Chrome |
| 滚动帧率 | 稳定 60fps | 连续滚动 10 秒无掉帧 |
| 排版开关切换 | < 150ms | 10 万行 |
| 标尺拖动 | 无可感知延迟 | 拖动全程不触发重排（沿用 v1.8 设计） |
| 内存占用 | 不超基线 2× | 50 万行对比 10 万行 |

## 5. 覆盖场景

- 10 万行以上长篇小说连续滚动阅读
- 排版开关反复切换、字号在 14–36px 间调整
- 平板上横竖屏切换、单指滚动 + 标尺拖动
- 手机上侧栏抽屉开合、纯净阅读模式
- 低配设备（集显 / 4GB 内存）可用性

## 6. 边界情况

| 情况 | 处理 |
|---|---|
| 极端超大文件（>100 万行） | 不追求全量流畅，给出提示并保证不崩溃、可正常分页 |
| 排版与标尺同时变更 | 合并为一次重排，避免抖动 |
| 移动端软键盘弹出 | 不引起视口高度抖动导致重排风暴 |
| 旋转屏幕 | 防抖处理后重算一次 |
| 后台标签页 | 暂停重排，回到前台再补算 |

- [x] 桌面端现有功能零回归（搜索 / 分页 / 进度 / 排版 / 标尺） —— 10 万行首屏 138 ms、排版切 15/12 ms、堆 28.2 MB、长任务 0。**渲染逐字节等价**：10 个视觉行位置（0 / 1 / 40 / 400 / 4k / 40k / 10 万 / 20 万 / 30 万 / 末尾）的 `#content.innerHTML` FNV-1a 指纹与改前逐个相同；**且是在「未补齐」状态下测的** —— 首屏正是在「lines 只有前缀、总数还是估算值」时画出来的。**搜索两态一致**：4 个查询（含 `*王*` 通配与无结果）在「分片未补齐」与「已补齐」下命中数、条数、顺序指纹全同

### 7.1 未达标项与遗留（诚实登记）

| 项 | 现状 | 原因 / 下一步 |
|---|---|---|
| **内存「不超基线 2×」（50 万行 vs 10 万行）** | **4.88× ✗**（10 万行 28.2 MB / 50 万行 137.6 MB） | 已复测（v1.18）。**非本轮引入**：改前同口径为 4.89×（31.8 → 155.6 MB），本轮反而降了 12%。真正的问题是这条判据本身 —— 数据量放大 5× 而限值只给 2×，而当前架构必然**全量持有**解码文本 + 逻辑行 + 视觉行（分片只改「何时构建」，不改「最终都建」）。要么复评判据（按线性放宽到 ~5×），要么单独立项做「视觉行按窗口回收」，不在本 PLAN 收口范围内 |
| 手机横屏正文仅 53 px | 可用但不宽裕 | 受限于 375 px 视高与四段占位（顶栏 94 + 翻页栏 62 + 标尺 44 + 状态栏约 40）。彻底解决需要横屏专用的紧凑顶栏，属新工作面，未纳入本次 |
| 移动端地址栏遮挡 | 未验证 / 未处理 | `.app` 用 `100vh`，在移动浏览器上等于「地址栏收起时」的高度，底部可能被浏览器 UI 盖住。改用 `dvh`/`svh` 有取舍（`dvh` 会随地址栏显隐反复触发 resize → 重排抖动，与 §6「软键盘弹出不引起重排风暴」相冲突），且 CDP 设备模拟无法验证地址栏行为。需真机复测后再定 |
| 补齐全过程中的页数会先小后正 | 50130 → 57241（+12%） | 见 `buildPages()` 注释。根因是 **vh 读数时机**而非行数估算：首次布局时横向滚动条尚未出现（448），补齐完成时已出现（436），`rowsPerScreen` 10 → 9、每页步进 8 → 7 行。Chrome 的滚动条占位要两轮布局才落定，同步 flush 拿不到最终值（已实测 `void offsetHeight` 无效）。只影响补齐前的约 1.6 s，且分片下此刻 `totalVisualRows` 本来就是估算值，一并由 `finishFill` 重算 |
